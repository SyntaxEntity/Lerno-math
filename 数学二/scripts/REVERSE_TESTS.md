# 校验器反向测试记录

> **为什么要有这个文件**：不做反向测试的校验等于自我安慰。408 项目吃过亏——
> 一条渲染校验因为判据写成「标记是否**出现**在该段」而不是「是否位于**段首**」，
> 字段粘连时标记落在段落中间，于是它一直报 0 条、完全失效。
> 所以本资料的每条校验规则，都用一个**最小反例**验过「它真的会报错」。

运行方式：

```bash
python3 数学二/scripts/reverse_tests.py        # 跑全部反例
python3 数学二/scripts/reverse_tests.py -v     # 同时打印命中的错误原文
```

当前结果：**48 条用例 / 48 条通过**，覆盖 F1—F23 全部规则（F12 见第三节说明）。

> **2026-10-15 补记**：本文件的用例表曾停留在 25 条，而 `reverse_tests.py` 早已加到
> 39 条（补了 F9 结构化、F19、F20、F21 等用例）——**文档与脚本脱节本身就是一种失效**，
> 因为读者会以为覆盖范围只有 25 条。现已逐条对齐，并新增第 40、41 条
> （F3 真实解析器层，成品模式与内容源模式各一条，见第二节第 7 条）。

## 二、反向测试当场抓出的 9 个真实缺陷

这一节是本文档最有价值的部分：**以下每一条都是「校验器本来没在工作」，
靠反例才暴露出来的。**

| # | 规则 | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | F10 / F11 | `validate_partial()` 里 `segs` 的值已经 `"\n".join()` 成**字符串**，却仍按列表遍历 | 逐字符迭代，正则永不匹配，**对全部 15 个文件恒报「0 条」**——看起来像内容违规，其实是校验器失效 | 改为 `segs[...].split("\n")` 后再逐行匹配 |
| 2 | F9 | 原判据是「中文句数 3—20 句」 | 数学文本里公式内标点极多，同一段能数出 8 句或 24 句，产生大量假警报 | 改用模板真正规定的**自然段数 2—5 段**作为判据，句数只作统计输出 |
| 3 | F18 | `check_figs()` 只在成品模式被调用 | 内容源引用坏图时 `--parts` 完全查不出来 | 把 `check_figs()` 提到模式分支之外，两种模式都跑 |
| 4 | F13 | 只把「标题」当作需要前后空行的块级元素 | 字段标签与上一段粘连时 F13 不报，**而 F14 因 Markdown 渲染恰好容忍这种情况也不报**——两层检查都漏 | 把 `**考频统计**`/`**核心讲解**` 等六个字段标签也纳入「前后必须空行」的块级元素 |
| 5 | F17 | 只做逐行 `$` 配对检查 | 一个「行间 `$$` 被写成单个 `$`」的错误永远查不出（它孤立成行，逐行看被当作定界符跳过） | 增加全文 `$$` 个数奇偶校验 |
| 6 | H（辅助） | `inner_mask()` 用「一直找到下一个 `$$`」的循环 | 遇到**未闭合**的公式块时，会把后面几十行正文全部标成「块内部」——实测 inner 从 17 行暴涨到 67 行，**导致 F17 的计数看到的是空集，规则静默失效** | 重写为显式状态机：只有独占一行的 `$$` 才开启块状态；**含公式的单行 `$$...$$` 不加 inner**（否则坏定界符会连同证据一起被屏蔽） |
| 7 | F3（解析器层） | 解析器脚本 `.tools/check_mermaid_math2.mjs` **不在仓库里**（被清理 `node_modules` 时一并删掉），`validate.py` 却只 `warn` 一句「跳过真实解析」 | 摘要行照旧打印「mermaid 真实解析通过 **0** 块」而**整份报告仍然全绿**——F3 退化成「永远通过」，页面上任何一张渲染失败的图都查不出来 | ① 解析器脚本移入受版本管理的 `数学二/scripts/check_mermaid.mjs`（只有 node 依赖留在 gitignore 的 `.tools/`）；② 解析器缺失 / 无 node / 返回码非 0 / 一块图都没扫到，**四种情况全部改成 error**，要跳过必须显式写 `--no-mermaid`；③ 补第 40、41 条反例（未加引号的圆括号标签，成品/内容源各一条），并让这两条用例**不关**真实解析器；同时让 F3 的扫描根跟着模式走（`--parts` 扫 `parts/`），否则写手在「改 parts → validate --parts」内层循环里根本看不到自己刚写坏的图 |

| 8 | F20（`$$` 判据） | 判据写的是「正文里**至少出现一次** `$$`」，而当时 KaTeX 的初始化配置（含 `'$$'` 字面量）就内联在页面里、且位于 `<main>` 之后 | **一个公式都没有的科目总览页也照样"通过"**——这条规则其实一直在靠一段无关的脚本文本满足，属于假通过 | P2 把脚本外置后真相暴露（总览页 `$$` 数 2 → 0）。判据改为**与内容源等量**：内容源有几处 `$$`，页面就必须有几处；反例「把 `$$` 全删」实测报错 |
| 9 | F20 / F22（反例本身） | 两条反例的注入锚点随 P2 外壳改版失效：占位符反例挂在已删除的 `#wrap` 上，翻页反例改的是**首章**（它的上一章本来就是 `href="#"` 占位） | 反例变成空操作 → 反向测试报「反例未改变内容」。**这正是反向测试存在的意义**：校验器改了、反例没跟上，只有这条机制会喊出来 | 占位符反例改挂契约类名 `.site-body`；翻页反例改到**中间章**；两处都加了 `assert`，锚点消失时直接报错而不是静默跳过 |

第 6 条尤其值得记：它是一个「校验器的辅助函数把待查证据藏起来」的例子。
如果只跑正常数据，`inner_mask` 看起来完全正常（干净文件下 inner = 16 行，
与手工核对一致）；只有造了「`$$` → `$`」这个反例，才暴露出它会吞掉整篇文档。

第 7 条是另一种更隐蔽的失效：**规则本身没写错，但它的执行前提没被满足，
而失败路径被写成了 warning**。判断办法很简单——问一句「这条规则今天到底跑了几次？」
本项目的做法是把次数打进摘要行（`mermaid 真实解析通过 N 块`），
**看到 0 就必须当成红的**，而不是当成「没图所以跳过」。

## 三、F12 的手工反向验证记录

F12 要求「README 声明的原题清单」与「正文标注」**双向**一致，两个方向都验过：

1. **方向一（README 多声明）**：临时在 `数学二/README.md` 的原题表里加一行
   `| \`2024\` | 第 \`99\` 题 | 选择题 |` → 校验器报
   `F12 声明为已核对原题但正文未标注：2024 年第 99 题`。
2. **方向二（正文多标注）**：临时把某章的真题标题改成
   `**2024 年数二第 98 题（选择题，5 分）**` → 校验器报
   `F12 正文标注为原题但未在 README 清单声明：2024 年第 98 题`。

两次都确认报错后已恢复。之所以不纳入自动化用例：README 由
`build_readme.py` 从 `parts/` 实扫生成，手工改 README 会被下一次构建覆盖，
做成自动化用例反而容易掩盖真实问题。

## 四、结论

- **48 / 48 条规则可被反例触发**，说明校验器确实在工作，而不是「一直报 0 条」。
- 反向测试过程中修掉 9 个真实缺陷（并为其中 4 条规则补了用例），其中 3 个（#1、#6、#7）属于**规则完全失效**级别，
  若不做反向测试会一直误以为「校验通过 = 内容没问题」。
- 每次改动 `validate.py` 或写作契约后，都应重跑
  `python3 数学二/scripts/reverse_tests.py` 确认没有把某条规则改成失效状态。
- **新增规则时必须同时加一条反例**，否则它只是一个「看起来在检查」的装饰。
